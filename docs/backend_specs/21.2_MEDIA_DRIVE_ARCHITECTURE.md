# 21.2 — ARQUITETURA DE MÍDIA: DRIVE COMO SUBSTRATO

**Status:** Normativo · complementa `21.1_CONTENT_APIS_AND_ENTITY_RESOLUTION.md`
**Origem:** ADR-004 (decisão de 2026-09-16)
**Verificação empírica de cabeçalhos:** 2026-09-16

---

## 1. PRINCÍPIO

> **A plataforma não hospeda um único byte de mídia do usuário.**
> Imagem, áudio e vídeo vivem no **Google Drive do próprio autor**. A plataforma guarda apenas o identificador do arquivo e os metadados em texto, e monta a experiência de reprodução de forma integrada — **sem redirecionar, sem interromper o fluxo, sem parecer que o usuário saiu do produto**.

Três consequências diretas:

1. **Custo de armazenamento da plataforma = zero.** A cota consumida é a do próprio autor (15 GB gratuitos por conta Google).
2. **Soberania do autor.** O arquivo é dele; revogar o compartilhamento retira a mídia da plataforma, sem pedido de exclusão.
3. **Compatível com a decisão "sem banco de dados"** — o que persiste é texto: um `fileId`, um tipo, uma duração, um título.

---

## 2. O CICLO CANÔNICO

```
  Usuário grava na plataforma (WebAudio / MediaRecorder)
                    │
                    ▼
        bytes existem LOCALMENTE no navegador
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
  extrair metadados        upload para o Drive
  AGORA, enquanto          do próprio usuário
  temos os bytes           (escopo drive.file)
        │                        │
        │                        ▼
        │                  fileId + compartilhar
        │                  "qualquer pessoa com o link"
        │                        │
        └───────────┬────────────┘
                    ▼
      Persistir APENAS TEXTO (~2 KB):
      { fileId, mimeType, durationMs, peaks[], title, provenance }
                    │
                    ▼
        Reprodução integrada na plataforma
```

**A decisão de projeto mais importante está no ramo da esquerda:** todo metadado caro de calcular — forma de onda, duração, pico, dimensões — é extraído **no momento do upload**, enquanto os bytes estão na memória do navegador. Depois disso, nunca mais precisamos dos bytes para renderizar a interface.

## 3. CAMINHOS DE ENTREGA — verificados

Cabeçalhos medidos em 2026-09-16 (com identificadores fictícios: o que se verifica é o comportamento do endpoint, não o arquivo).

| Caminho | CORS | Emoldurável | Veredito |
| :--- | :--- | :--- | :--- |
| `lh3.googleusercontent.com/d/<id>` | ✅ **`Access-Control-Allow-Origin: *`** | — | **Preferencial.** Bytes acessíveis por `fetch`, `<img>`, `<audio>` |
| `lh3.googleusercontent.com/d/<id>=w1200` | ✅ | — | Imagem redimensionada pelo Google |
| `drive.google.com/thumbnail?id=<id>&sz=w400` | ❌ | — | Serve em `<img>`; não serve para `fetch`/canvas |
| `drive.google.com/file/d/<id>/preview` | reflete origem | ✅ sem `X-Frame-Options` | Iframe de vídeo/PDF |
| `drive.google.com/uc?export=download&id=<id>` | ❌ | — | **403 — descontinuado.** Não usar |

> **Achado relevante:** `lh3.googleusercontent.com` responde com `Access-Control-Allow-Origin: *`. Isso significa que os bytes de um arquivo compartilhado publicamente podem ser buscados por `fetch` de origem cruzada — e portanto processados por Web Audio.
>
> **Ressalva honesta:** o teste foi de cabeçalho, com id fictício. Validar ponta a ponta com um arquivo real é item de implementação antes de depender disso.

## 4. EXPERIÊNCIA POR TIPO DE MÍDIA

### 4.1 Imagem — nativa, indistinguível

```html
<img src="https://lh3.googleusercontent.com/d/{fileId}=w1200" alt="{alt}" loading="lazy">
```
Sem iframe, sem marca do Drive, sem clique que leve para fora. **Visualmente idêntico a uma imagem hospedada.** É o caso ideal.

### 4.2 Áudio — nativa, com forma de onda pré-computada

```
┌──────────────────────────────────────────────────────────┐
│  ▶   Chaconne · BWV 1004                          2:14   │
│      ▁▂▅▇▆▃▂▁▂▄▆▇▅▃▁▁▂▃▅▇▆▄▂▁▂▅▇▆▃▁                     │
│      ●───────────────────────────────  0:47 / 2:14       │
│      🔊 ──●────                                          │
└──────────────────────────────────────────────────────────┘
```

O player é **da plataforma** — `<audio>` nativo com controles próprios. A forma de onda vem do array `peaks[]` calculado no upload (≈ 2 KB de números), **não** de reprocessar o áudio a cada visualização. O Drive é apenas a origem do `src`.

Resultado: a pessoa vê um player da Academia. O byte vem do Drive.

### 4.3 Vídeo — iframe, com ressalva declarada

```html
<iframe src="https://drive.google.com/file/d/{fileId}/preview"
        allow="autoplay" allowfullscreen loading="lazy"></iframe>
```

🟠 **Limitação que precisa ser dita:** o player de vídeo do Drive tem identidade visual do Google. Diferente da imagem e do áudio, **o vídeo não fica indistinguível**. Três caminhos:

| Opção | Aparência | Custo |
| :--- | :--- | :--- |
| Iframe do Drive | player do Google dentro do nosso enquadramento | zero |
| YouTube não listado | player do YouTube | zero, mas a mídia sai do Drive |
| `<video>` nativo apontando para `lh3` | nativo | requer validação de streaming por faixa (`Range`) |

**Recomendação:** iframe do Drive na v1, com moldura, título e ações da plataforma **ao redor** dele, de modo que o vídeo seja um elemento da nossa página — não uma página do Google. Validar a terceira opção antes da v2.

## 5. ESCOPOS OAuth E COMPARTILHAMENTO

| Escopo | Classificação Google | Para quê |
| :--- | :--- | :--- |
| `drive.appdata` | **não sensível** | Backup JSON privado (ADR-001.A) |
| `drive.file` | **não sensível** | Criar e gerenciar **apenas os arquivos que o app criou** |

`drive.file` é exatamente o escopo correto: dá acesso aos arquivos que a plataforma enviou, e **a nada mais do Drive da pessoa**. Nenhum dos dois exige verificação restrita nem auditoria CASA.

**Compartilhamento:** para que outra pessoa veja a mídia, o arquivo precisa de permissão `anyone with the link` (`role: reader`, `type: anyone`), aplicada pela API no momento da publicação.

🔴 **Consentimento explícito obrigatório.** "Qualquer pessoa com o link" significa acessível a quem tiver a URL, fora do controle da plataforma. A interface **precisa** dizer isso em linguagem clara antes de publicar, e oferecer o caminho de despublicar (remover a permissão, voltando o arquivo a privado).

## 6. O QUE A PLATAFORMA PERSISTE

```ts
/** Referência de mídia. Texto puro — nunca bytes. */
export interface DriveMediaRef {
  readonly fileId: string;
  readonly kind: 'IMAGE' | 'AUDIO' | 'VIDEO' | 'PDF';
  readonly mimeType: string;
  readonly title: string;

  /** Extraídos no upload, enquanto os bytes estavam locais. */
  readonly durationMs?: number;
  readonly width?: number;
  readonly height?: number;
  /** Envelope da forma de onda, 0–100, ~400 pontos ≈ 2 KB. */
  readonly peaks?: readonly number[];
  readonly byteSize: number;

  readonly ownerSubject: string;
  readonly visibility: 'PRIVATE' | 'LINK_PUBLIC';
  readonly publishedAt?: IsoDateTime;

  /** Presente quando a mídia lastreia uma evidência auditada. */
  readonly evidenceId?: EntityId;
}
```

Peso típico: **~2,5 KB por mídia**, dominado pelo array de picos. Mil gravações no índice compartilhado ≈ 2,5 MB — e mesmo isso nunca trafega inteiro, porque a busca roda na Function (ADR-003).

## 7. COMO ISSO ATRAVESSA O PRODUTO

| Onde | Mídia | Entrega |
| :--- | :--- | :--- |
| Perfil — Gravações | áudio do autor | player nativo + picos |
| Perfil — Portfólio | áudio, vídeo, PDF | player nativo · iframe · iframe |
| Estúdio — render do projeto | áudio | upload ao Drive, player nativo |
| Sala — entrega de tarefa | áudio ou vídeo | player embutido na fila de correção do professor |
| Comunidade — anexo | imagem, áudio | `<img>` nativo · player nativo |
| Academia — manuscritos, gravuras | **não é do Drive** | Commons / IMSLP, conforme `21.1` |
| Prática — áudio de exercício | **não é do Drive** | síntese WebAudio local |

> **Fronteira:** mídia **do usuário** → Drive. Mídia **de acervo histórico** → Commons/IMSLP com proveniência (`21.1 §5`). Mídia **didática gerada** → síntese e SVG programáticos. Nunca misturar as três origens.

## 8. FALHAS PREVISTAS E TRATAMENTO

| Falha | Tratamento |
| :--- | :--- |
| Autor revogou o compartilhamento | Estado explícito: "mídia indisponível — o autor restringiu o acesso". **Nunca** player quebrado |
| Arquivo excluído do Drive | Mesmo estado; oferecer remoção da referência |
| Cota do Drive esgotada no upload | Erro claro com o tamanho do arquivo e o espaço disponível |
| Limite de taxa do Google | `retry` com espera exponencial; a interface degrada para a capa estática com os picos |
| Sessão expirada durante upload | Reautenticar e retomar; nunca perder a gravação — manter em `IndexedDB` até confirmar |

---

## 9. CRITÉRIOS DE ACEITE

1. Nenhum byte de mídia do usuário em `localStorage`, KV ou no bundle.
2. Imagem e áudio renderizam **sem iframe** e sem marca visual de terceiro.
3. Forma de onda vem de `peaks[]` pré-computado — nunca de reprocessar áudio em tempo de visualização.
4. Publicar exige consentimento explícito e informado sobre "qualquer pessoa com o link".
5. Existe caminho de despublicar que efetivamente revoga a permissão.
6. Mídia indisponível tem estado próprio — nunca player quebrado.
7. Gravação sobrevive a falha de upload (retomada a partir de `IndexedDB`).
8. Escopos limitados a `drive.appdata` e `drive.file`.
